# Data model
Owner: architect. Consumers: data-engineer (migrations, data-access module), backend, tests, security-reviewer, sre (backups, purge).
Postgres, plain-SQL migrations (dbmate), Kysely. Decisions behind this: ADR-0004 (budgeting), ADR-0005 (money and time), ADR-0006 (tenancy).

## Conventions (apply to every table)
- **IDs:** `uuid`, UUIDv7, generated by the application (DAL) unless the database version provides `uuidv7()`. Composite or natural PKs only where stated.
- **Timestamps:** `timestamptz`, stored UTC. Every table has `created_at`; every mutable table has `updated_at`. Values that rules depend on (expiries, windows, `created_at`, "today") come from the application's injectable clock so tests can freeze time (test-hooks.md); `DEFAULT now()` is only a fallback.
- **Money:** `bigint` USD cents. No floats or `numeric` in storage or arithmetic. Amount columns carry a range `CHECK`. Currency is fixed: `budgets.currency = 'USD'` by `CHECK`.
- **Calendar values:** transaction dates are `date`. Months are `date` with `CHECK (extract(day from month) = 1)`.
- **Versioning:** user-editable rows (`budgets`, `categories`, `plan_entries`, `transactions`) have `version integer NOT NULL DEFAULT 1 CHECK (version >= 1)`, incremented by exactly 1 on every update. Updates are `... WHERE id = $1 AND version = $2`; zero rows updated → `VERSION_CONFLICT`.
- **Tenancy:** every budget-owned table has `budget_id NOT NULL`. Child rows reference parents with **composite FKs that include `budget_id`**, so a row can never point at another budget's data. Every DAL function takes a `BudgetScope` (ADR-0006) and filters by its `budget_id`.
- **Text:** trimmed, Unicode NFC, no control characters. Length limits are counted in Unicode code points (same as JSON Schema `maxLength`), enforced in the API and by `CHECK (char_length(x) BETWEEN …)` in the database. Emails use `citext` and are stored lowercased.
- **Enums:** Postgres enum types or `text` + `CHECK`. Values match the API exactly.
- **Soft delete:** only `budgets` and `transactions` (`deleted_at`). Everything else is deleted for real or archived. Soft-deleted rows are invisible to every API read and are purged after 30 days.
- **Roles:** `migrator` owns the schema and runs migrations (its URL, `MIGRATOR_DATABASE_URL`, is given **only** to the migrate job, never to the service or admin jobs). `app` has `SELECT/INSERT/UPDATE/DELETE` on tables and `USAGE` on sequences only (no DDL, no `TRUNCATE`), except `security_events` (INSERT and SELECT only). Admin commands use `app`. `backup` has `SELECT` only and is used only by the nightly `pg_dump` in the `shoestring-backup` Cloud Run job (OD-4; ADR-0007 constraint 10). Its credential lives only in Secret Manager. Neon's default owner role is never used by any component. Every database URL uses `sslmode=verify-full` and a long random password (the free-tier database is reachable from the internet).
- **Application keyring `APP_KEYRING` (F-24, replaces `MFA_ENCRYPTION_KEY` and `THROTTLE_KEY`):**
  - **Format:** JSON `{"current":"k2","keys":{"k1":"<base64>","k2":"<base64>"}}`. Key IDs match `^k[0-9]{1,4}$`. Each key is exactly 32 random bytes, and keys differ per environment.
  - **Startup check:** the keyring is validated at startup (JSON shape, `current` present, every length); the server refuses to start otherwise.
  - **Subkeys:** raw keys are never used directly. Subkeys come from HKDF-SHA-256 with salt `shoestring` and info `totp-v1`, `recovery-code-v1`, `throttle-v1` or `cursor-v1`.
  - **Versioned uses** (`totp_credentials`, `recovery_codes`): store `key_id`. New rows always use `current`; reads use the row's key.
  - **Unversioned uses** (throttle keys, cursor MACs): always use `current`. Rotating therefore orphans at most 24 h of rate-limit counters and invalidates outstanding cursors (clients restart at page 1).
  - **Rotation check:** `GET /api/readyz` fails if any row references a key ID missing from the keyring, so the deploy gate blocks a keyring that dropped a key still in use. `readyz` is public, so the 503 body is the generic `UNAVAILABLE` message: it never names key IDs, counts or tables. The detail goes only to the server log (key IDs are Internal).
  - **Rotation procedure:** add a key → make it `current` → `rewrap-mfa` (admin-commands.md) → remove the old key once `rewrap-mfa --dry-run` reports no rows on it. Recovery-code hashes cannot be rewrapped; they move off an old key only when users regenerate codes.
  - **Escrow:** an offline escrow copy of the keyring lives in a password-manager vault separate from the backup `age` key (owner ruling, round 2). It is never stored with backups.

## Data classification
| Class | Meaning | Rule |
|---|---|---|
| **PII** | Identifies a person: email, display name, IP address, user agent | Never in logs, Sentry, or analytics. Shown only to the user and, where stated, to co-members. |
| **Sensitive** | Financial or personal user content: amounts, payee, memo, budget names, category names, plan amounts | Never in logs or Sentry. Only in API responses to budget members, in the CSV export, and in backups. |
| **Secret** | Credentials: password hashes, session token hashes, CSRF tokens, TOTP secrets, recovery-code hashes, one-time token hashes, WebAuthn challenges | Never leave the backend; never in responses (except TOTP secret and recovery codes shown once at setup), logs, or exports. |
| Internal | IDs, timestamps, enums, counters | May be logged. IDs are opaque UUIDs. |

Derived values: `idempotency_keys.request_hash` is **Internal, derived from Sensitive** (a hash of a body containing payee, memo and a low-entropy amount): never logged, never returned, kept 24 h.

### user_tokens (one-time email tokens)
| Column | Type | Class | Notes |
|---|---|---|---|
| id | uuid PK | | |
| user_id | uuid FK → users ON DELETE CASCADE | | |
| purpose | enum `password_reset` \| `email_change` \| `email_change_cancel` | | |
| token_hash | bytea UNIQUE NOT NULL | **Secret** | |
| email | citext NULL | **PII** | `email_change`: the requested new address. `email_change_cancel`: the previous address to revert to (where the cancel link was sent). |
| requested_by_session_id | uuid NULL FK → sessions ON DELETE CASCADE | | `email_change` only: revoking the requesting session deletes the token (F-01) |
| mfa_failed_attempts | smallint NOT NULL DEFAULT 0 | | token is invalidated at 5 |
| created_at, expires_at | timestamptz NOT NULL | | reset: 30 min; email change and cancel: 24 h |
| used_at | timestamptz NULL | | |

Invariants (DB): `CHECK ((purpose = 'password_reset') = (email IS NULL))`; `CHECK ((purpose = 'email_change') = (requested_by_session_id IS NOT NULL))`; partial unique index `(user_id, purpose) WHERE used_at IS NULL AND purpose <> 'email_change_cancel'` (issuing a new reset or email-change token deletes the open one). Cancel tokens are **not** unique per user: each email change keeps its own cancel link to its own previous address, so a later change cannot replace an earlier victim's link.
Invariants (app), F-01: these events delete every open `user_tokens` row of the user **except `email_change_cancel`**, in the same transaction: password change, password-reset completion, revoke-others, admin `revoke-sessions`, admin `reset-mfa`, any MFA factor added or removed, account-deletion request, email-change confirm (other tokens), email-change cancel. Cancel tokens survive so that an attacker who controls the account cannot erase the victim's way back; they expire after 24 h. The single exception is `revoke-sessions --all --restore` (F-11), which deletes them too.
Invariants (app), **F-33 (cancel-token chain):**
- Using an `email_change_cancel` token deletes the user's open tokens other than cancel tokens, **plus only the cancel tokens with a later `created_at`**. Earlier cancel tokens stay open: the earliest open cancel token always wins. Ties are broken by `id`; ids are UUIDv7, so ordered by creation.
- `POST /me/email-change` is refused (429, `Retry-After` until expiry) while the user has any open `email_change_cancel` token, so at most one email change can be started per 24 h.
- Cancel and revert email both the address restored or kept and the address abandoned.
- Index `(user_id, purpose, created_at)` for these lookups. The regression tests are spelled out in auth.md §9.

### budgets
| Column | Type | Class | Notes |
|---|---|---|---|
| id | uuid PK | | |
| name | text NOT NULL (1–60) | **Sensitive** | |
| timezone | text NOT NULL | | IANA name, validated by the API; defines "today" and "current month" only |
| currency | char(3) NOT NULL DEFAULT 'USD' CHECK (currency = 'USD') | | kept for a future multi-currency ADR |
| created_at, updated_at, version | | | |
| deleted_at | timestamptz NULL | | soft delete; restorable by its owner until `deleted_at + 30 days`, then purged (ADR-0010) |

Restore (`POST /me/deleted-budgets/{deletedBudgetId}/restore`, through `DeletedBudgetScope`, F-36) clears `deleted_at` and bumps `version`. It is refused with `LIMIT_REACHED` when the **owner** is already a member of 10 non-deleted budgets, or when **any other member** would end up in more than 20 non-deleted budgets. The response never names the member (F-37). A restore is therefore the only way a member can pass 10. Memberships, invitations, categories, plans and transactions are untouched by soft delete, so they come back as they were. Invitations that expired meanwhile stay expired.

### budget_members
| Column | Type | Notes |
|---|---|---|
| budget_id | uuid FK → budgets ON DELETE CASCADE | |
| user_id | uuid FK → users ON DELETE CASCADE | |
| role | enum `owner` \| `member` NOT NULL | |
| joined_at | timestamptz NOT NULL | |
PK `(budget_id, user_id)`. Index `(user_id)`.
Invariants (DB): **exactly one owner per budget**: partial unique index `(budget_id) WHERE role = 'owner'` (at most one) plus a `DEFERRABLE INITIALLY DEFERRED` constraint trigger on `budgets` insert and `budget_members` delete/update that fails the transaction if a non-deleted budget has no owner row (at least one). Invariants (app): ≤ 6 members per budget. **Ownership transfer** (ADR-0010) runs in one transaction with `SELECT … FOR UPDATE` on the `budgets` row: first update the current owner's row to `member`, then the target's row to `owner` (in that order, because the partial unique index is checked per statement); the deferred trigger confirms exactly one owner at commit. The target must be a member whose account `status = 'active'`.

### transaction_splits
Every transaction has **1 to 20** splits. An ordinary (unsplit) transaction has exactly one split carrying the full amount, so every read and the summary have a single code path.
| Column | Type | Class | Notes |
|---|---|---|---|
| id | uuid PK | | |
| budget_id | uuid NOT NULL | | |
| transaction_id | uuid NOT NULL | | FK `(budget_id, transaction_id)` → `transactions(budget_id, id)` ON DELETE CASCADE |
| category_id | uuid NOT NULL | | FK `(budget_id, category_id)` → `categories(budget_id, id)` ON DELETE **RESTRICT** |
| amount_cents | bigint NOT NULL CHECK (1 ≤ amount_cents ≤ 100000000) | **Sensitive** | |
Unique `(transaction_id, category_id)`. Index `(budget_id, category_id)`, `(transaction_id)`.
Invariants (DB): **splits sum to the parent and there is at least one**, enforced by a `DEFERRABLE INITIALLY DEFERRED` constraint trigger on insert/update/delete of `transaction_splits` and on update of `transactions.amount_cents`, which checks at commit that `count(*) BETWEEN 1 AND 20` and `sum(amount_cents) = transactions.amount_cents` for each affected transaction. The API checks first and returns `SPLITS_DO_NOT_SUM`; the trigger is the backstop (a trigger failure is a 500 and a bug).

| Categories per budget | 100 | `LIMIT_REACHED` |
| Splits per transaction | 20 | `VALIDATION_FAILED` |
| Passkeys per user | 10 | `LIMIT_REACHED` |
| Active sessions per user | 20 | least recently seen evicted |
| `mfa_pending` sessions per user | 5 | oldest pending evicted |
| Amount per transaction, split or plan entry | $1,000,000.00 (100000000 cents) | `VALIDATION_FAILED` |

## Derived values (computed on the server only)
- **Month of a transaction:** the `YYYY-MM` of its `date`. No timezone conversion.
- **Budget today / current month:** the app clock's current instant converted to `budgets.timezone`.
- **Month summary:** ADR-0004 formulas over non-deleted transactions with `date` in the month, joined to their splits.

## Deletion and purge
Run by the daily `purge` admin command (admin-commands.md); each step is idempotent and logs only counts.
- **On deletion request** (`POST /me/deletion`, one transaction): `SELECT … FOR UPDATE` every budget the user owns (F-25); refuse with `OWNS_SHARED_BUDGET` if any owned, non-deleted budget has another member (the user can transfer ownership first, ADR-0010); otherwise set `status = 'pending_deletion'`, revoke pending invitations of budgets the user owns, delete all of the user's sessions, and delete all open `user_tokens` (F-01). Cancelling restores `status = 'active'` (revoked invitations stay revoked).

1. Users with `status = 'pending_deletion' AND purge_after <= now()`: lock and **re-check with the same rule as the deletion request (F-35):** no **non-deleted** budget they own has another member. If one does (only possible through a bug or a race), skip that user, log a counts-only line, and fail the run so the purge alert fires (F-25). Otherwise delete every budget they own, **including soft-deleted ones still inside their restore window** (members were notified at deletion; the restore window ends when the owner is purged, and the "account deletion scheduled" email says so), then delete the user.
2. Budgets with `deleted_at <= now() - 30 days`: hard delete (CASCADE to members, invitations, categories, plan entries, transactions, splits).
3. Transactions with `deleted_at <= now() - 30 days`: hard delete (CASCADE to splits).
4. Expired rows: sessions, `webauthn_challenges`, `user_tokens` and `signup_invites` past expiry for 7 days, unconfirmed TOTP setups older than 15 min, `idempotency_keys` and `auth_throttles` older than 24 h, `security_events` older than 90 days (via `purge_security_events()`), non-pending invitations answered more than 30 days ago and pending ones expired more than 30 days ago.
Backups are not rewritten; they expire within 35 days (ADR-0007: 34-day lifecycle), so purged data is gone everywhere within 30 + 35 days. **After a restore from backup** the runbook runs `revoke-sessions --all` and then `purge` (admin-commands.md) before reopening, because a restore brings back revoked sessions, removed members, old password hashes and removed MFA factors (F-11).

## CSV export
UTF-8, RFC 4180, header row, one file per request. Amounts are decimal dollars with two places (`12.34`), never negative (direction is its own column). Cells starting with `=`, `+`, `-`, `@`, tab or CR are prefixed with `'`.
- `transactions`: `budget_name, transaction_id, date, direction, total_amount, split_category, split_amount, payee, memo, created_by, created_at_utc` (one row per split; `created_by` is the member's display name or empty).
- `plans`: `budget_name, month, category, category_kind, planned_amount`.
Scope: every non-deleted budget the user is a member of, including entries made by co-members. The export iterates the user's memberships and obtains each `BudgetScope` through `requireMembership` (no raw join, F-18). Every user-text column (budget name, category, payee, memo, created_by) gets the formula-injection prefix.

## Required indexes for performance (EXPLAIN-checked by data-engineer)
- Transaction list: `transactions (budget_id, date DESC, id DESC) WHERE deleted_at IS NULL`; category filter via `transaction_splits (budget_id, category_id)`.
- Month summary: the list index for the month range, plus `transaction_splits (transaction_id)` and `plan_entries (budget_id, month)`.
- Membership check (every budget request): `budget_members` PK.
